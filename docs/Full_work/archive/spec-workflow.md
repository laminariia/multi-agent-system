# Workflow: от идеи к спецификации

> Как мы пришли к Pipeline A spec. Повторяемый процесс для любого компонента системы.

---

## Этап 1: ТРИ ВЗГЛЯДА

Берём компонент (pipeline, модуль, страницу) и смотрим на него с трёх сторон:

### View 1: Что реально делает код

Читаем исходники. Не документацию, не планы — **код**. Записываем:
- Какие функции вызываются, в каком порядке
- Какие таблицы БД используются
- Какие есть invariants (например: HITL mandatory для bid)
- Что НЕ делает код (важнее чем то что делает)

**Формат:** ASCII-схема потока + список "Что НЕ делает код".

### View 2: Видение пользователя

Пользователь описывает **как он хочет** чтобы это работало. Своими словами, без технических ограничений. Описывает:
- Что видит на экране
- Какие действия совершает
- Какие результаты ожидает
- Как это ощущается в работе

**Формат:** User story в свободной форме.

### View 3: Что описано в документации но не реализовано

Собираем из всех `docs/plans/`, `docs/*.md`, спецификаций:
- Дизайн-документы с пометкой "❌ не реализовано"
- Фичи из roadmap которые застряли
- Архитектурные решения которые приняты но не воплощены

**Формат:** Список с пометками статуса (❌/⚠️/✅).

---

## Этап 2: МАТРИЦА ПЕРЕСЕЧЕНИЙ

Накладываем три взгляда друг на друга:

| Пересечение | Значение | Действие |
|-------------|----------|----------|
| Код ✅ + Видение ✅ + Доки ✅ | **Работает** | Ничего не трогать |
| Видение ✅ + Доки ✅ + Код ❌ | **GAP** | Реализовать первым — есть и дизайн и потребность |
| Видение ✅ + Код ❌ + Доки ❌ | **НОВОЕ** | Спроектировать с нуля |
| Код ✅ + Видение ❌ | **Под вопросом** | Спросить — нужно ли это? |

Матрица показывает **что делать первым** без гадания.

---

## Этап 3: УТОЧНЕНИЕ

Показываем пользователю матрицу. Он:
- Подтверждает / отвергает / корректирует
- Добавляет **новые концепции** которые не были ни в коде ни в доках
- Принимает архитектурные решения (RAG-память, типы сдачи, лимиты параллельности)

**Ключевой принцип:** видение пользователя = source of truth. Технические детали дополняют, но не перекрывают.

---

## Этап 4: ЕДИНАЯ СПЕЦИФИКАЦИЯ

Объединяем всё в один документ:
- **Структура** — от видения (user story по фазам)
- **Детали** — из кода и документации (таблицы БД, API, state machine)
- **Новое** — из уточнений (RAG, delivery types)
- **Приоритеты** — P0 (blockers) → P1 (ядро) → P2 (сложное) → P3 (расширение)

Формат: Phase 1..N, каждая фаза описывает что происходит от лица пользователя + технические детали реализации.

---

## Этап 5: РАЗДЕЛЕНИЕ

Финальный документ разделяется:
- **Аналитика** (три взгляда + матрица) — остаётся в `docs/vision/{component}.md`
- **Спецификация** (source of truth) — выносится в `docs/vision/{component}-spec.md`

Аналитика — для понимания контекста. Спецификация — для реализации.

```
docs/vision/
├── pipeline-a.md        ← три взгляда + матрица (контекст)
└── pipeline-a-spec.md   ← единая спека (source of truth)
```

**Что вошло в спеку:**

## Что можно улучшить

### В процессе

1. **Формализовать View 2 раньше.** Мы начали с кода (View 1), потом спрашивали видение. Лучше: сначала видение пользователя (без привязки к коду), потом код, потом доки. Так видение чище — не загрязняется знанием ограничений.

2. **Шаблон для user story.** Вместо свободной формы — структурированные вопросы по каждой фазе: "Что ты видишь? Что нажимаешь? Что ожидаешь? Что бесит если не работает?"

3. **Версионирование спеки.** Сейчас спека — один файл. При изменениях теряется история решений. Добавить changelog или дату у каждого изменения.

4. **Отдельно фиксировать РЕШЕНИЯ.** "Почему 3-5 параллельных диалогов а не 10?" "Почему RAG в P2 а не P1?" — decision log чтобы не переспрашивать.

### В спеке

5. **Acceptance criteria для каждого P-уровня.** Сейчас P0-P3 — список задач. Добавить: "P0 закрыт когда: Scout → Bid → HITL → submit проходит end-to-end за < 5 мин."

6. **Зависимости между задачами.** Некоторые P1 задачи зависят от P0. Нарисовать DAG зависимостей чтобы не блокироваться.

7. **Метрики успеха.** Для каждой фазы — как измерить что она работает: конверсия бидов, время отклика, accuracy скоринга.

8. **Edge cases.** Что если клиент не отвечает 7 дней? Что если платформа заблокировала аккаунт? Что если LLM галлюцинирует цену? — пограничные сценарии для каждой фазы.
